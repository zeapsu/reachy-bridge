How Hermes is wired into the Reachy console

Four processes on the robot host, two transports between the app and the agent, and one camera path that is deliberately still disconnected. Everything drawn solid exists on main today; everything dashed is an open issue in the current milestone.

1 · Processes and transports

The controller never talks to Hermes. It launches the app and watches a marker file; the app owns the agent. Nothing in the controller imports or calls anything from reachy_hermes, and the daemon is not Hermes-aware — the only coupling is process supervision plus a ready file.

The daemon owns the physical devices, but it is not the only process reading the camera: apps attach as independent GStreamer IPC consumers of the daemon's published stream, and the dashboard lease is deliberately left running while a vision app is up. One app at a time is enforced by the supervisor, not by the camera.

Specifics behind the boxes: the daemon is launched through tools/reachy_mini_daemon_jetson.py, but the camera and audio-level routes themselves are defined in tools/reachy_mini_daemon_media.py and installed only when the host is a Jetson — on a Mac simulation daemon those routes do not exist at all. The dashboard stream is leased through DashboardCameraLeaseManager; speech is faster-whisper base.en in and kitten-nano out; and the agent runs under a version-scoped HERMES_HOME=~/.cache/reachy-hermes/v0.19.0/home, so a rollback to a previously accepted release resumes that version's own state with no migration.

connection.json and the native client are drawn as hazards because the descriptor contains the WebSocket URL including the session token. The local WebSocket has no per-connection authentication, so the entire trust boundary is the loopback bind plus the secrecy of that file — and because every tool call is auto-approved, the toolset allowlist is the only thing bounding what an attached client can do. That is the reason #104 starts by not publishing the descriptor.

The topology says what exists; it cannot say in what order it comes up. That ordering is where the readiness issues live, so it gets its own view below.

Steps 9 through 15 are the whole of issue #108: readiness is currently declared once the two speech models are warm, so a dead gateway, a missing plugin, or an unhealthy snapshot path all leave the controller reporting a healthy app. Model pre-warm failures are logged and retried lazily rather than being fatal — also on #108's list.

The two camera boxes on the right of view 1 never meet today. CameraMJPEGStreamer already holds latest_jpeg and frame_sequence for the dashboard stream — #106 hangs a single-use capability off that existing state rather than opening a second capture device, and #107 is the only thing allowed to redeem it.

2 · One voice turn

Each step gates the next. Completion is event-driven: the gateway's message.complete is the single authoritative answer, and message.delta is dropped precisely because it can carry intermediate tool payloads. The VAD keeps a 0.45 s pre-roll so the first syllable survives, and config.set yolo=on lands on the session native clients also attach to — see section 3.

While a turn is in flight, mic input is rerouted to a second detector: a bare stop or cancel interrupts the session, and anything else is queued onto the live turn as a follow-up — or held in _pending_followups and answered by a standalone turn if the original one already committed.

Two things this view leaves out. Head wobbling is suppressed for the duration of a turn and restored after, and every stage marks activity onto a conversation event bus that the settings UI consumes over SSE. And this is not the only way a turn can start — the relay in section 3 is a second, concurrent turn source.

The turn is genuinely unbounded today: no timeout wraps the wait for message.complete. The only timeouts in the gateway are for process boot and the gateway.ready event. That is precisely the hole #105 fills.

3 · The two edges that explain the backlog

Neither is on the happy path, and between them they account for most of what is still open in the milestone.

The native-session relay

A background task polls the agent over plain HTTP every 0.75 s, separate from the JSON-RPC socket, and speaks any turn it did not originate — so a prompt typed into the native TUI comes out of the robot's speaker. External turns hold _processing_turn with no cap, which is how #96 stayed stuck until the controller stopped the app. #104 removes the descriptor and the relay.

hermes.py · _relay_native_session

yolo=on is never reset

Auto-approval is sent on every ask() against the shared, persistent session and is never turned back off, so TUI-submitted tool calls skip the approval gating the TUI would normally provide. With HERMES_TUI_TOOLSETS=all and no per-connection auth on the socket, the allowlist #104 introduces is the actual security boundary.

gateway.py · ask, HERMES_TOOLSETS

Voice cancel was unreachable

#96's third deficiency, and the least obvious: during the loop the mic kept triggering on noise, but VAD stripped essentially every 30 s capture, so no transcript ever formed and no stop could be recognised. The cancel path existed and could not be reached. Still true today — nothing skips a capture whose VAD output is empty.

hermes.py · _process_cancel_utterance

4 · Runtime pin and the compatibility gate

The gate is a ceremony, not a runtime component: it runs offline against a candidate binary and its output is what may be copied into the pin. At app startup only the cheap half runs — a --version parse compared against the pin.

The gate's live checks drive a throwaway reachy_probe plugin under apps/reachy_hermes/.hermes/plugins/ that returns a fixed base64 JPEG behind a one-shot nonce file. It is scaffolding that proves the mechanism exists — not the production camera tool.

What the gate established about the Hermes surface

  • A plugin delivers an image into the active turn by returning {"_multimodal": true, "content": [image_url data URI], "text_summary": …} straight from the tool handler — no second prompt.submit, no upload RPC, no file path. The check passes only when the model's answer names a colour and a word it could only get from the pixels.
  • There is no Hermes-native single-use primitive. Fail-closed behaviour is implemented in the plugin's own Python using an out-of-band nonce file. That is exactly why #106 needs an app-side broker rather than a platform feature.
  • Provider and model identity are scraped by walking the payload for provider/model-shaped keys — there is no documented Hermes field, which is why the pin records them as unrecorded rather than guessing.
  • Project-local plugin discovery is opt-in, requiring HERMES_ENABLE_PROJECT_PLUGINS=1, and is proven by matching a debug log line from a real hermes serve.
  • The no-raw-persistence check scans the scratch state directory and the child's captured output for JPEG magic bytes and base64 fragments. It cannot say anything about what an upstream provider does with the bytes once they leave the host, and does not claim to.

Where vision is stubbed today

  • _request_completion takes image_jpeg and immediately deletes it.
  • The app builds ToolDependencies with camera_worker=None and vision_processor=None, and no-ops MediaManager._init_camera so it never opens a competing device.
  • The safety prompt ends with an explicit instruction not to claim camera sight.

6 · What is traced, and what is inferred

Every solid box and edge was followed in source at f92f2bb and independently re-verified against the app, controller, and daemon packages, the merged pull requests for #101 to #103, and the retained decision record. Nothing here was observed running on the robot.

The most important caveat is not about the diagrams. This map describes main. The robot host has none of #101, #102, or #103 deployed — it is still running the pre-pin, pre-marker-strict build. Any behaviour you check on hardware today will not match views 1b or 4.

Schematic rather than literal

  • Tailscale Serve is operator configuration in the robot owner's shell, not in this repository. The controller itself only binds 127.0.0.1:7861.
  • The DaemonProxy edge is drawn to the daemon's media box for readability; the proxy actually carries full-state WebSocket, controls, stats, and media status alike, and it is the controller's only path to the daemon API.
  • The browser edge lands on AppSupervisor to show what the operator triggers; requests really arrive at the controller's routes, which call it.

Upgraded from inference to mechanism

The native-client edge was previously guesswork on my part. It is not: the descriptor the gateway writes contains the WebSocket URL with the session token embedded, so publishing it is what makes an attached native client possible. The hazard is structural, not incidental.

Still uncertain

  • The dashed edges are issue text, not implementation. #106's split across a daemon route and an app-side broker follows the recorded design decision, but no code for it exists yet; if it lands differently, this map is wrong there first.
  • Nothing here describes the upstream Hermes binary's own source, which was never read. The RPC and event surface shown is what our client sends and what the compatibility gate observed — a claim about our code and about measured behaviour, not about Hermes' documented API.
  • Multiple simultaneous camera IPC consumers are allowed and tested at this repository's boundary, but whether the daemon's GStreamer producer guarantees it lives in the external SDK, outside this workspace.
